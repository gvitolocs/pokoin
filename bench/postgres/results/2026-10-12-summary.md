# Postgres 19beta4 vs 17.11 on Pokoin's workloads: summary (2026-10-12)

Detailed reports with every round are next to this file:
- [main run, production-like settings](2026-10-12-17.11-vs-19beta4.md), with correctness, resources and the snapshot writes;
- [default vs default](2026-10-12-default.md);
- [19 with `io_method=sync`, reads and batch jobs](2026-10-12-19-io-sync.md);
- [19 with `io_method=sync`, snapshot writes](2026-10-12-writes-19-io-sync.md) and [TPC-B](2026-10-12-tpcb-19-io-sync.md).

## Verdict

- **The upgrade itself is sound.** `pg_upgrade` 17.11 → 19beta4 works. Every query, the whole nightly rebuild and the price analytics return identical output on both versions, and the `pokoin-rust` database tests pass on 19.
- **Reads gain a little, from the engine itself.** The card desk is 7–10% faster on 19 with production-like settings, and search and the set page use about 8% less CPU per request. The card-desk gain is still there, slightly larger, with 19's new asynchronous I/O switched off (`io_method=sync`), so it comes from the engine and not from the I/O path.
- **The nightly `sold_daily` rebuild doesn't get faster.** It takes about 25 s on both versions. The difference is inconclusive with production-like settings (+3%) and with the sync control (−2%), and 6% faster only on stock settings.
- **19's default I/O mode (`io_method = worker`) costs Pokoin.** With it, vacuum is 17–23% slower and book upserts 7% slower, and on stock memory settings the card desk loses 23%. With `io_method=sync`, the vacuum and upsert costs disappear and listing writes become 28% faster than on 17.
- **Generic TPC-B is 16–17% slower on 19beta4, with either I/O mode.** Pokoin's own write paths don't show it. Re-check on 19 GA.
- **A 7–10% read gain is not a reason to run a beta.** On the 19 GA schedule this is a modest, real improvement, provided the writer sets `io_method` explicitly. At GA, measure again on production data: `scripts/postgres-major-upgrade.sh rehearse` keeps a 17 copy and its 19 upgrade side by side on nezopt for `run.py`.

## How it was measured, and the four checks

1. **Identical environments.**
   - Both servers run in the same container: 4 vCPU, 15 GB RAM.
   - Both load the same settings file, which mirrors the writer's flags with memory halved.
   - For reads and batch jobs, the 19 cluster is `pg_upgrade --link` of a byte copy of the 17 cluster, so data, indexes and planner statistics are identical.
   - For writes, one dump is restored into both servers as a template, and every run starts from a fresh copy of it.
   - 53 settings still differ because 19 has new settings and new defaults. All are listed in the main report; the ones that matter are in the last table below.
2. **No simultaneous runs.** Exactly one benchmark runs at a time, and the first server alternates every round. The idle server keeps its memory (2 × 2 GB shared buffers fit in 15 GB). Nothing else ran on the machine during measurements.
3. **Variation, not single numbers.**
   - Every round is reported, with its median and spread.
   - A difference is called only when it is at least 5% and every round of one server beats every round of the other. Anything else says "inconclusive".
   - Runs are 3 rounds × 30 s. That's enough for the 7–28% effects above, not for anything near 2–3%.
   - The 17 baseline itself moved up to ±10% between sessions (listing writes: 450–509 tps in one session, 515–565 in another), so only comparisons within the same session are used.
4. **Pokoin first.** The nightly rebuild, analytics, card desk, search, set page, listing writes (with their audit trigger) and CardTrader book upserts come first. The generic pgbench tests are labelled *generic*.

Limits:
- The data is synthetic: real dictionary names and a synthetic CardTrader book, 2.5 GB in total.
- The builds are from source without LLVM, so JIT ran on neither side. The official images include LLVM, and their 17 defaults to `jit=on` while 19 defaults to `jit=off`.
- `io_uring` was not tested.
- There was no replica attached.

## Writes from identical snapshots (19 vs 17, production-like)

Each run is 16,000 listing writes or 200,000 book upserts, with the same seed on both servers. The end state was identical on every run and server: the same counts and price sums, so no update was lost.

| measure | listing writes, 19 `worker` | listing writes, 19 `sync` | book upserts, 19 `worker` | book upserts, 19 `sync` |
| --- | --- | --- | --- | --- |
| tps | +2.6% inconclusive | **+27.6% better** | **−7.2% worse** | −2.9% inconclusive |
| p50 / p95 / p99 | **+7.1%** / −3.6% / −2.3% | 0.0% / **−23.6%** / **−20.7%** | **+7.0% / +6.0% / +7.7%** | +2.6% / +0.9% / +1.7% |

| table / index growth, dead tuples | equal | equal | equal | equal |

Generic TPC-B tps is **−17.3%** with 19 `worker` and **−15.6%** with 19 `sync`.

## Defaults that change with 19 (they matter for the cutover)

| setting | 17.11 | 19beta4 | what to do on the writer |
| --- | --- | --- | --- |
| `io_method` | (none) | `worker` | Set it explicitly: `sync` measured best here; test `io_uring` if the image and Docker's seccomp profile allow it. |
| `jit` | `on` | `off` | Decide explicitly. Production 17 runs JIT on the big analytic queries today. |
| `effective_io_concurrency` / `maintenance_io_concurrency` | 1 / 10 | 16 / 16 | Keep the new defaults on NVMe. |
| `default_toast_compression` | `pglz` | `lz4` | Fine. New TOASTed jsonb compresses faster. |
| data checksums (`initdb`) | off | on | Must match for `pg_upgrade`: the writer stays off. |
| planner | | `enable_self_join_elimination`, `enable_eager_aggregate` on | Nothing to set; part of the read gains. |

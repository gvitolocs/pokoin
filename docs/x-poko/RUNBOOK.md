## What this build adds

All changes are in `pokoin-rust/apps/poko-bot`, with workspace lockfile updates.

- `youtube.rs`: H17 Poko callback implementation, F17 compatible token JSON,
  authorization/code exchange, refresh-token preservation, channel verification,
  YouTube REST transport, retry after HTTP 401, and typed disabled-comment errors.
  Writes use unique 0600 temporary files, fsync and atomic rename. Existing token
  files must have no group/other permissions. Refreshes serialize within one
  client; concurrent independent processes must not own the same token file.
- `x_client.rs`: X27/X28 OAuth 1.0a HMAC-SHA256, H37 CRC/signature primitives,
  X REST calls for posts, users, tweets/search and following.
- `social_text.rs`: card-X and J16 pure selection/text/daily guard functions,
  engagement ordering with decimal snowflake IDs, UTF-16 text limits, YouTube
  Short classification and ISO duration parsing.
- `hospital.rs`: explicit configurable P-OPS incident client and dead-port guard.
- `main.rs`: explicit OAuth/config commands. The daemon also serves the OAuth route when POKO_BOT_OAUTH_ADDR is explicitly
  configured; with that variable absent its existing listeners and ownership are unchanged.

The native command entry points are:

```sh
poko-bot youtube-auth
poko-bot youtube-auth --code-file /path/to/0600-authorization-code
POKO_BOT_OAUTH_ADDR=127.0.0.1:8791 poko-bot youtube-oauth-serve
poko-bot check-hospital-config
```

The daemon may use the same loopback-only OAuth listener through POKO_BOT_OAUTH_ADDR, without a second process. Do not start the standalone listener on an already-owned port.

The auth commands use credentials from the environment. The callback server
binds loopback only and starts no poller. No command above was run against a
production OAuth account. Public proxy routing is not installed by this change.
One resolver sets the YouTube data directory for the daemon, `youtube-auth` and
`youtube-oauth-serve`: `POKO_BOT_DATA_DIR`, else `POKO_BOT_STATE_DIR`, else
`/var/lib/poko-bot`, and an empty value is absent rather than a directory.
`POKO_YOUTUBE_TOKEN_PATH` overrides its `youtube-poko-token.json`. Preserve the
existing live token path at handover, or copy it privately with owner/mode checks
before changing config. `POKO_BOT_OAUTH_ADDR` follows the same rule: empty means no
OAuth listener at all, so an unset or empty value cannot abort the daemon on address
parsing.
Client id/secret precedence follows live Cityhop/Gmail then Google aliases;
the redirect defaults to the live `http://127.0.0.1:8788/oauth2callback`.
Set `CITYHOP_YOUTUBE_REDIRECT_URI` explicitly to the registered public callback.

Intentional changes: OAuth recovery text names the Rust CLI, authorization codes
come from 0600 files rather than process arguments, token errors redact provider
bodies, and token files are repaired to 0600 on replacement. The hospital client
floors `POKO_HOSPITAL_TIMEOUT_MS` at 10 seconds. A token save that fails after a
successful refresh is an error, not a warning: the caller must not carry on with an
access token that was never persisted. The OAuth `state` stays the constant `poko`
as in Node, so it is not a CSRF nonce; that is only acceptable because the listener
binds loopback and starts no poller. This callback implements the Poko flow; the old
Cityhop/Griffin dispatcher is not restored.
General HTTP method/dispatcher and success/error HTML parity are not yet fully
certified, so H17/F17 remains unverified in the retirement gate.

## Why poko-youtube-replies fails

At 19:21–19:22 UTC on 2026-10-22 the log ends with a YouTube
`commentThreads.list` failure: the video has disabled comments. Discovery catches
that error per announcement; the later watched-video loop makes the same request
outside a per-video catch. It escapes `main()` and sets exit code 1, leaving the
systemd service failed. OpenRouter 429s precede this but successfully fall back to
DeepSeek; they are not the terminating exception.

The native REST client recognizes `commentsDisabled` and `videoNotFound` through
`comments_unavailable`. The **one-pass poller still needs porting**. That port must
skip just the unavailable video, continue others, and persist state after the
pass; quota/auth errors must remain visible. Do not report the live job as fixed.
Also preserve an observed Node bug deliberately only after review: the live
script computes `DRY = Boolean(args.dry)`, so bare `--dry` is false. Never run that
Node script under the assumption that bare `--dry` prevents publishing.

## P-OPS Hospital destination

Set the full Rust incident URL explicitly, for example using your **verified**
Rust listener/tailnet DNS name:

```dotenv
POKO_HOSPITAL_URL=http://<lucina-rust-host>:<rust-listener-port>/api/internal/bot-hospital/incident
POKO_HOSPITAL_TOKEN=<provision privately>
POKO_HOSPITAL_TIMEOUT_MS=60000
```

The endpoint belongs to P-OPS H45, not the Poko health server. `18789` on p2 is
not that endpoint. The live Node source defaults to a different local tunnel,
`18788`, and its live env file was confirmed to override this with the dead
`18789`. The native client does not guess either tunnel and rejects port 18789 on
every loopback spelling — `localhost` in any case, any `127.` address including the
`127.1` shorthand, `[::1]` and the IPv4-mapped `[::ffff:127.0.0.1]` — compared on the
parsed host, so brackets and case do not slip past it. It requires a token whenever
a URL is configured. Secret aliases retain Node precedence:
POKO_HOSPITAL_TOKEN, POKO_NEWS_ALERT_TOKEN, BOT_HOSPITAL_TOKEN,
HERMES_INTERNAL_ALERT_TOKEN. URL aliases: POKO_HOSPITAL_URL then POKO_NEWS_ALERT_URL.
Timeout minimum 10 seconds, default 60 seconds. No request is sent by the
`check-hospital-config` command. The live env file has neither POKO_HOSPITAL_TOKEN nor BOT_HOSPITAL_TOKEN; the other aliases or systemd environment may still supply a token. Endpoint reachability and authentication still
need testing against the deployed P-OPS Rust service; its actual production
address was not established here. Nothing changed on p2.

## Validation

Run in this worktree, without bot credentials or a GPU:

```sh
nice -n 10 env CARGO_BUILD_JOBS=3 CARGO_TARGET_DIR=/tmp/x-poko-target \
  cargo test --manifest-path pokoin-rust/Cargo.toml -p poko-bot --locked
nice -n 10 env CARGO_BUILD_JOBS=3 CARGO_TARGET_DIR=/tmp/x-poko-target \
  cargo clippy --manifest-path pokoin-rust/Cargo.toml -p poko-bot --locked --all-targets -- -D warnings
cargo fmt --manifest-path pokoin-rust/Cargo.toml -p poko-bot --check
bash -n pokoin-rust/apps/poko-bot/deploy/x-poko-cutover.sh
```

`token_refresh_model.rs` model-checks two refresh callers and a crash at any step,
over the ordering of the refresh call and the real token merge. Its write and rename
steps are model states, so it does not exercise `write_token`, the temporary file,
fsync or the rename itself; those are covered by the `youtube_oauth` tests, not by
the model. What it checks is serialization, refresh-token retention, committed
access tokens and reachability of both completed callers. This is a
finite protocol abstraction, not a proof of OS durability or of unported money
flows. LoL bets need their own Stateright/Verus work before J10 can be verified.

## 0. Summary

- **The dictionary** is three generated ES modules in `market/src/data/`:
  `suggest-names.js` (10,009 `{display, prior}` rows), `suggest-sets.js`
  (838 `{display, slug, prior, nationality}`) and `suggest-artists.js`
  (444 `{display, slug, prior}`). Together they are **574.6 KB raw, 95.6 KB
  gzip-9 and 75.2 KB brotli-11** as JSON (588.0 KB / 95.8 KB / 75.4 KB as
  the files on disk). The web keeps them in memory and ranks every keystroke
  locally; the network is used only to fetch printings for the names the
  local ranker picked.
- **"7 MB → 600 KB" is history only.** The three files total 601,445 bytes
  (≈ 600 KB) in the commit that introduced them (`4ef3028`, 2026-09-16); no
  commit in the 1,272-commit GitHub history records a 7 MB predecessor (§2.2).
  The current figure, 574.6 KB raw / 75.2 KB brotli, is the baseline the
  app has to match or beat, not a target to aim for.
- **The current Flutter app has no local dictionary.** Every keystroke is
  ranked by the server: `POST /api/marketplace-autocomplete` after a 120 ms
  debounce, plus `POST /api/searchbar-token-predict` after 35 ms (§3.1). The
  first-pass audit also found that these calls build their URL with
  `Uri.base.resolve('/api/…')`, which on Android and iOS does not point at
  `api.pokoin.com`. That has to be confirmed on a device first (§3.1, F1).
- **Target:** ship the dictionary as **PKD1**, a binary string pool with
  fixed-width columns (§4.1). It is 337.8 KB raw / 114.1 KB gzip-9 /
  92.8 KB brotli-11. It is 17.6 KB bigger than the web's 75.2 KB brotli,
  almost all of it two columns the browser computes at runtime and Dart cannot
  compute without extra libraries: collation ranks and the compacts of 611
  non-ASCII rows (without the ranks it is 76.8 KB). Carrying the same parity data as tuple JSON costs
  430.0 KB / 121.4 KB / 95.3 KB, so PKD1 is the smaller option in every
  column. Once loaded, the whole dictionary plus its search indexes is
  **≈ 1.1 MB of typed arrays** (computed from measured byte counts, §4.2).
  For comparison, importing the web engine grows V8's heap by **24.5 MB**.
- **The ranker is ported to Dart with behavioural parity** to the web,
  enforced by golden fixtures generated from the JS engine (§4.7). Production
  serving of the dictionary is a **Rust** route (§4.4). Node is only allowed
  for local build tools and tests.

## 2. What "the dictionary" is (verified)

### 2.1 Files, rows and generators

| file | rows | row shape | bytes on disk | generator |
| --- | ---: | --- | ---: | --- |
| `market/src/data/suggest-names.js` | 10,009 | `{display, prior}` | 484,421 | `scripts/export-suggest-names.py` |
| `market/src/data/suggest-sets.js` | 838 | `{display, slug, prior, nationality}` | 91,038 | `scripts/export-suggest-catalog.py` |
| `market/src/data/suggest-artists.js` | 444 | `{display, slug, prior}` | 26,675 | `scripts/export-suggest-catalog.py` |

- **Names** come from `marketplace_card_names` joined to `marketplace_cards`,
  one row per `compact_name`. `display` is the most-printed spelling and `prior`
  is its printing count (minimum 1). They are ordered by prior desc, then
  display (`export-suggest-names.py`, the `SQL` constant). Max prior: 428
  (Pikachu).
- **Sets** come from `pokoin_pokemon_expansions` and `marketplace_set_card_counts`.
  `slug` is re-slugified in Python (`slugify`), `prior` is the catalog card
  count, and `nationality` is one of `western, japanese, chinese, american,
  french, product, indonesian, korean, idth`. Max prior: 819. Note that the c1 dictionary's
  `nationalities` table (`market/src/compact-dictionary.json`) has no
  `american` or `french`, so the mobile format keeps its own palette (§4.1).
- **Artists** come from `marketplace_blueprint_artists`; `prior` is the
  artist's card count (max 5,120, 5ban Graphics).
- Non-ASCII displays: 564 names, 44 sets, 3 artists.
- The scripts run `psql` inside the `pokoin-marketplace-postgres-15t` container
  through `docker exec`, so they only work on the database host.
  `export-suggest-catalog.py` also regenerates
  `market/src/data/expansion-nationality.js` (`scripts/export-expansion-nationality.mjs`).

At import, the engine derives more structures from these rows. The counts
below were measured by `measure-dictionary.mjs`:

| derived structure | where | size |
| --- | --- | ---: |
| `NAME_POOL` (`{display, compact, prior}`) | `suggest-rank.js:602` | 10,009 rows |
| `ARTIST_POOL` (full names plus surname rows ≥ 5 letters) | `suggest-catalog.js:23-45` | 685 rows |
| `SET_POOL` | `suggest-catalog.js:46` | 838 rows |
| set-alias pool (era names, extras, `COLLECTOR_ERA_ALIASES`) | `suggest-rank.js:1132-1192`, built from `tcg-eras.js` | 430 rows |
| name-token vocabulary (`NAME_TOKEN_LIST`) | `search-score.js:278-289` | 3,672 tokens, 23,643 UTF-8 bytes |
| name-token postings (`NAME_TOKEN_TO_DOCS`) | same | 34,785 entries |

The set-alias logic also depends on `TCG_ERA_CATALOG` in `market/src/tcg-eras.js`
(30,108 bytes of source), and product/single classification depends on
`suggestKind` in `market/src/identity.js`. Both are part of what has to be
ported (§4.5).

### 2.2 The "7 MB → 600 KB" line

What the history shows (full GitHub history, 1,272 commits, cloned blobless
into a scratch directory; the session checkout is shallow from 2026-10-07):

- The three data files first appear in `4ef3028` (2026-09-16, "Catch the repo
  up to the Pi-first production state"), at 484,421 + 90,615 + 26,409 =
  **601,445 bytes**. That is the "600 KB". They have not been restructured
  since: `suggest-names.js` has the same size today, and sets and artists grew
  by a few hundred bytes.
- No commit message, doc or code comment in either repository mentions a 7 MB
  dictionary (`git log --all -i -E --grep='[0-9.]+ ?MB'`, plus a grep over
  `docs/`, `market/`, `scripts/` and `pokoin-rust/`). The typeahead's earlier
  history lived in the canonical checkout on nezopt and was not pushed to
  GitHub, so the 7 MB artifact could not be identified. See open question Q1.
- Nearby real reductions, for context only: the SPA main bundle went from
  3.2 MB to 1.75 MB raw (`e3121ba`, route splitting). The React entry chunk
  went from 1.39 MB to 819 KB raw (brotli 307 → 224 KB) once the suggest
  engine and its data moved to a chunk loaded on search intent (`51cae0f`).
  The 5ban artist list went from 6.5 MB of JSON to 1.4 MB as c1 (`bd3b33c`).
  And `cde4dda` made per-keystroke ranking cheap ("7 pikachu keystrokes on a
  fresh pool 17-21 ms vs 88-96 ms exhaustive", Node).

The guide treats the line as history. The baseline is today's 574.6 KB raw /
75.2 KB brotli.

| --- | ---: | ---: | ---: | --- |

### 2.4 How the web loads and uses it

- **One lazy chunk, loaded on search intent.** `market/src/suggest-engine.js`
  re-exports the engine. `suggest-engine-loader.js` imports it once and
  retries if the import fails. The Solid app (`solid/src/lib/suggest-engine.js`,
  100% canary per `docs/frontend-perf/PLAN.md`) loads it on pointer-down,
  focus or the first input, and `index.html` prefetches the chunks at idle
  priority without evaluating them (PLAN.md B3). Ranking stays on the main
  thread: rank workers re-parsed the 10k catalog per worker and were dropped
  from the header (`f94e61e`). Only ScanDesk still starts workers.
- **Cold cost in Node** (7 fresh processes, p50; three invocations): importing
  `suggest-rank.js` + `suggest-catalog.js` takes 57–64 ms, and the whole engine
  (plus `search-score.js`, `suggest-resolve.js`, `suggest-live.js`) takes
  167–175 ms. The V8 `heapUsed` delta after `gc()` is **24.5 MB** (24,459,320 B in
  the last run). That is the cost of the per-entry object graph: row objects,
  token arrays, `Map`s and memo tables. The Dart design avoids it (§4.2).
- **Per keystroke** (Node, first call for each prefix of 10 queries, 108
  keystrokes, `rankNames` + `parseTypedQuery`): p50 5.8–7.1 ms, p95
  13.7–17.8 ms, max 67–92 ms. The max is the first call (JIT warm-up). The
  in-browser figure on the mobile profile (390×844, CPU throttle ×4) is in
  `docs/frontend-perf/RESULTS.md` run ab2: Solid keystroke → visible rows changed p50 307 ms /
  p95 547 ms, INP p50 104 ms. That includes network hydration.
- **Paint path** (Solid `SearchBox.jsx` → `paintCatalogGroups`, `suggest-live.js:605`):
  `liveSuggestGroups` parses the query (`parseTypedQuery`), classifies the
  intent (`catalogIntent`) and resolves hypotheses (`resolveSuggestQuery`).
  It then either scores cached printings with the free-text model
  (`search-score.js` `scoreGroups`) or ranks the name pool (`rankNames`), and
  `fillSuggestGroups` caps the popup at 20 printings, applying the
  tab/print-language/mechanic rules. Printings come from the in-memory live
  cache (`byCompact`, 30-minute TTL, 2,500 names max, `suggest-live.js:53-55`),
  which network hydration fills (§4.8).

### 2.5 Related but separate: c1, `/api/dictionary` and the dcb dictionary

`docs/rust-migration/COMPACT_ENCODING.md` describes three things that are
*not* the typeahead dictionary, though the app will meet them:

- **c1 / c1v2** is a columnar encoding of read responses (`?format=c1`),
  decoded by `market/src/compact.js`. Since `e6bcf0f` the web requests c1
  from `/api/marketplace-suggest` too. A Dart client either omits
  `format=c1` and gets plain JSON (works today), or ports `compact.js`.
  COMPACT_ENCODING.md §6 step 7 says "a Dart decoder is the same ~200 lines".
- **`GET /api/dictionary`** serves the append-only code tables c1 is coded
  against (`market/src/compact-dictionary.json`, version 1). It is needed
  only if the app decodes c1.
- **`GET /api/c1-dictionary`** is the RFC 9842 `dcb` brotli shared dictionary
  for list snapshots. It is **not live**: Cloudflare passthrough was turned
  off on 2026-10-10 (COMPACT_ENCODING.md §3.5). Mobile HTTP stacks do not
  negotiate `dcb`, so it does not apply to the app.

## 4. Target design

### 4.1 File format: PKD1 everywhere

**Decision:** one binary format, PKD1, for the bundled asset, the on-disk
copy and the network body. The reference implementation is `pkd1.mjs`. The
mobile file is produced locally with
`node docs/handoff/flutter-suggest-dictionary/measure-dictionary.mjs --write-pkd1 <out>.pkd1`.

Layout (little-endian; every section starts on a 4-byte boundary, so Dart can
take `Uint16List`/`Uint32List` views without copying):

```text
0   'PKD1'                          magic
4   u16 formatVersion = 1
6   u16 sectionCount
8   u8[16] contentHash              first 16 bytes of SHA-256 over the canonical tuple JSON
24  u32 names, u32 sets, u32 artists
36  sectionCount × { u8[4] tag, u32 offset, u32 length }

STRS  UTF-8 pool: name displays, set displays, set slugs, artist displays,
      artist slugs, then the shipped compacts (names, sets, artists)
NDLN SDLN SSLN ADLN ASLN   u8 byte length per string (every row is < 256 bytes; max 77)
NPRI SPRI APRI             u16 prior per row (max 5,120)
NCXI SCXI ACXI             u16 row index of each row whose display is not pure ASCII
NCXL SCXL ACXL             u8 byte length of that row's compactQuery output
NCOL SCOL ACOL             u16 rank of each display under the web's `new Intl.Collator()`
SNAT                       u8 index into NATP per set
NATP                       nationality palette: u8 count, then (u8 len, UTF-8) per value
```

Why this layout, measured against the alternatives (§2.3):

- **Smallest once parity is included.** The browser gets two things for free
  that a Dart port does not. `String.prototype.normalize` drives
  `compactQuery` for non-ASCII text, and `Intl.Collator` breaks score ties in
  `rankNames` (`suggest-rank.js:911-917`). Dart's core library has neither. So
  the mobile file carries the compacts of the 611 non-ASCII rows and a
  collation rank per row. With that data, PKD1 is 337.8 / 114.1 / 92.8 KB
  against 430.0 / 121.4 / 95.3 KB for tuple JSON. It is also 41% smaller raw
  than the web's 574.6 KB object JSON, and that raw size is what the device
  reads from storage and keeps in RAM.
- **No parse.** Load means: read the bytes, check the magic and hash, create
  views, and make one prefix-sum pass that turns lengths into offsets. ASCII
  compacts are derived in the same pass, as lowercase with everything outside
  `[a-z0-9]` dropped, which is exactly `compactQuery`'s ASCII branch
  (`market/src/compact-query.js`). This takes 1.4–1.9 ms in Node, against
  1.3–2.2 ms for `JSON.parse` of the tuple JSON alone, which still leaves
  ~11k lists and ~22k strings to convert afterwards.
- **Lengths instead of offsets** keep the file smaller, and rebuilding offsets
  costs one linear pass. **Shipping every compact** was measured and rejected:
  557.9 KB raw / 146.0 KB brotli, because lowercase compacts do not match
  their displays well under LZ.
- The wire size is 17.6 KB brotli above the web format, 16.0 KB of it the
  collation-rank columns (76.8 KB without them). That cost is paid once per dictionary version. Open
  question Q4 lists cheaper encodings for NCOL if this matters.

### 4.2 In-RAM layout and memory budget

One immutable `SuggestDictionary` object holding typed data only:

| component | type | bytes (from measured counts) |
| --- | --- | ---: |
| file buffer (STRS + columns, kept as views) | `Uint8List` | 345,880 |
| compact pool, **as UTF-16 code units** (see P1 in §4.5) | `Uint16List` | ≤ 418,616 (209,308 UTF-8 bytes × 2, upper bound) |
| offsets: name display + compact, set display + compact + slug, artist display + compact + slug | `Uint32List` × 8 | 95,488 |
| names sorted by compact (exact lookup, prefix ranges) | `Uint16List` | 20,018 |
| token vocabulary for the scorer (3,672 tokens, UTF-16) | `Uint16List` + `Uint32List` offsets | ≤ 47,286 + 14,692 |
| token → names postings (34,785) | `Uint16List` + offsets | 69,570 + 14,692 |
| name → tokens forward index (`langText.en.name` per name doc) | `Uint16List` + `Uint32List` offsets | 69,570 + 40,040 |
| **total resident dictionary** | | **≈ 1.14 MB upper bound** |

Per-query scratch (the reused DP rows, `Float64List`, which grow to the
longest name) and the bounded memo tables (`RANK_MEMO_MAX` 32,
`INTENT_MEMO_MAX` 24, resolver `SPAN_MEMO_MAX` 512, compact memo 20,000)
come on top. The live printing cache (≤ 2,500 names, 30-minute TTL) holds
API rows and is not part of the dictionary. **Budget: Dart heap delta ≤ 2 MB
after load and a 50-query corpus; RSS delta ≤ 6 MB** (§5.3). The web's V8
heap grows by 24.5 MB for the same data and engine (§2.4). The Dart figure is
**to be measured** with DevTools → Memory → diff snapshots (§3.2 step 5).

What the design rules out: a `Map` per entry, a `String` per entry held for
the life of the app, and `List<List<dynamic>>` from `jsonDecode`. `String`
objects are created only for the ≤ 20 visible rows, by `utf8.decode` of a
`Uint8List.sublistView`.

### 4.3 Loading, refresh and fallback

```text
first frame ──► (idle or search intent) ──► SuggestDictionaryStore.load()
                                              │
             disk copy valid? ── yes ─► read file ─┐
                    │ no                            ├─► Isolate.run(decode) ─► ready
             bundled asset ─────────────────────────┘        (TransferableTypedData / Isolate.exit, no copy)
                                              │
             background: GET /api/catalog/version ─► newer? ─► GET /api/catalog/names?v=…&format=pkd1
                                                                └─► verify hash ─► write temp, fsync, rename ─► swap
```

- **Bundled asset** `assets/suggest/dictionary.pkd1`, generated by the build
  step and committed or produced in CI. Q3 decides which. A first run after
  install is therefore fully local.
- **Disk copy** in `getApplicationSupportDirectory()/suggest/<hash>.pkd1`
  (`path_provider` is already a dependency), with the current hash in
  `shared_preferences`. Files are only replaced atomically (temp file, flush,
  rename). Keep the previous copy until the new one has been read and passed
  validation.
- **Decode off the UI isolate.** `await Isolate.run(() => decodePkd1(bytes))`.
  `Isolate.run` exits with `Isolate.exit`, which hands the result to the
  caller without copying, so typed arrays built in the worker arrive at no
  cost. On a cold start the asset read is `rootBundle.load` (a `ByteData`) or
  a `File.readAsBytes` of the disk copy. Both are async.
- **When to warm up.** Following the web (PLAN.md B3, `51cae0f`), start
  `load()` after the first frame, at idle or on the first focus of the search
  field, whichever comes first. Do not load it before `runApp`. The
  benchmark gate (§5.3) compares cold start with and without the dictionary.
  If decode p95 on the low-end device stays under one frame, eager loading
  after the first frame is also acceptable.
- **Refresh** at most once per app start and every 24 h. `GET /api/catalog/version`
  (`max-age=300`) is cheap. The body is fetched only when the version
  differs. Whole-file replacement, not deltas: 92.8 KB brotli does not
  justify a delta protocol (Q5).
- **Fallback.** If the dictionary is missing or invalid (bad magic, unknown
  `formatVersion`, hash mismatch, truncated sections), drop that copy, fall
  back to the bundled asset, and log the event. If no valid dictionary is
  available at all, the search box uses the network path: the same requests
  the web's satellite-game path makes (`GET /api/marketplace-suggest?q=<typed>&limit=20`,
  `solid/src/components/SearchBox.jsx:330-350`), with server order and no
  local rank. While the dictionary is loading, the popup shows a pending
  state, as the web does (`suggestPending`, `SearchBox.jsx`).

### 4.4 The Rust endpoint (planned, not on main)

`origin/feature/cache-sync-engine` (`45ae489`, `docs/handoff/cache-sync/README.md`)
plans `GET /api/catalog/names?v=<ver>`, returning
`{v, names:[[display,prior]], sets:[[display,slug,prior,nationality]], artists:[[display,slug,prior]]}`,
immutable per content-hash version, and `GET /api/catalog/version` → `{v}`
with `max-age=300`. **Neither exists on main**: there is no `catalog/names`
anywhere in `pokoin-rust/`. The web PLAN.md lists the request as accepted
(Phase F).

What the app needs from it (implemented in `pokoin-rust/`, e.g.
`crates/catalog-api/src/reads/`, next to `reads/dictionary.rs`, which already
shows the versioned, ETag'd, immutable pattern):

1. `GET /api/catalog/version` → `{"v":"<32 hex>"}`, `Cache-Control: public, max-age=300`, ETag.
2. `GET /api/catalog/names?v=<v>` → tuple JSON as planned (the web's shape).
   `&format=pkd1` returns the PKD1 bytes (`application/octet-stream`,
   `x-pokoin-format: pkd1`), compressed with brotli at the origin as the list
   snapshots are (`apps/api/src/lists.rs`). Both representations are
   `public, max-age=31536000, immutable` for a pinned `v`; an unknown `v`
   answers `409` like `/api/dictionary`.
3. **Built by a Rust job**, not a Node or Python script. It reads the same
   SQL as `export-suggest-names.py` / `export-suggest-catalog.py` and runs in
   the same place as `pokoin-api job build-lists` (k3s CronJob on nezopt,
   `bd3b33c`). It needs Rust equivalents of `compactQuery` (NFKC → strip δ →
   NFD → strip U+0300–U+036F → NFC → lowercase → keep letters and numbers)
   and of `Intl.Collator()` root ordering (for example `icu_collator`). Both
   are **gated** by the golden tables in `fixtures/compact.json`, plus a
   collation-order fixture to add next to it. Until the job exists, the app
   ships only the bundled asset generated by `measure-dictionary.mjs --write-pkd1`.
   That is a local build tool, which AGENTS.md allows.
4. The content hash is the first 16 bytes of SHA-256 over the canonical tuple
   JSON (`pkd1.mjs` `contentHash`). The web and the app then share one version
   string (today's data: `45fad7bea59ac13721bf002c6b3d378f`).

Put the engine in a **pure Dart package** with no Flutter dependency, e.g.

Parity pitfalls (each one is covered by a fixture):

- **P1: UTF-16, not UTF-8.** The DP compares `charCodeAt` values (UTF-16
  code units), and compact lengths drive `maxDistance` and the suffix weight.
  Keep compacts as `Uint16List` code units. Running the DP over UTF-8 bytes
  would change distances for the 611 non-ASCII rows (`é` is 2 bytes but 1
  code unit). Dart `String.codeUnits` matches JS exactly.
- **P2: Collation.** Ties are broken by `Intl.Collator().compare(display)` in
  `compareRanked`, by `localeCompare` in `orderSuggestGroups`,
  `fillSuggestGroups` and `scoreGroups`, and by a numeric collator for
  printing ids. Dictionary rows use the shipped NCOL/SCOL/ACOL ranks. Strings
  that only arrive at runtime (group names absorbed from API rows, set names,
  collector numbers) need a Dart comparator that approximates root collation;
  the paint fixtures are the gate.
- **P3: Stable sort.** `Array.prototype.sort` is stable, and `rankNames`
  relies on that (`suggest-rank.js:984-989`). Dart's `List.sort` is **not**
  guaranteed stable. Use `mergeSort` from `package:collection`, or add the
  row index as the last key.
- **P4: Floating point.** Scores mix `Math.exp`, `Math.log1p` and divisions.
  Dart's `exp` and `log` are IEEE doubles too, but `log1p` must be written as
  `log(1 + x)` with the same rounding. Fixtures round to 1e-9. Compare
  orderings exactly and scores after rounding.
- **P5: Regex semantics.** `\b`, `/i`, `\p{L}\p{N}` with the `u` flag
  (`compactQuery`, `nameTokens`) must use `RegExp(..., unicode: true)` in
  Dart. `MODIFIER_NAME` and the `displayHasModifier` patterns must be copied
  verbatim and checked by the `mods` fixture field.
- **P6: Memo eviction** order (insertion-ordered `Map`, first key evicted).
  Dart's `LinkedHashMap` preserves insertion order, so the same code
  translates directly.

  frame of the keystroke reads as instant. The web reaches warm `rankNames`
  on a desktop-class Node in single-digit milliseconds (p50 5.8–7.1 ms for the
  first call per prefix, §2.4), so a typed-array port with the same cutoff DP
  has room to fit a frame on mid/high devices. The low-end limit (50 ms)
  allows for slower cores; it is still about an order of magnitude below the
  web's mobile-profile keystroke-to-rows p50 of 307 ms (RESULTS.md ab2),
  which includes network time.
- **25% of the old p50**: the old path waits at least the 120 ms debounce plus
  a round trip (F3) before anything can render, while the new path renders
  local results first.
- **2 MB heap / 6 MB RSS**: the computed resident size is about 1.14 MB
  (§4.2). The limits allow for memo tables, the live printing cache and
  allocator overhead, and are still more than ten times below the web's 24.5 MB V8 delta.
- **150 KB package delta**: PKD1 is 114.1 KB gzip-9, which approximates a
  deflated asset in the APK, plus the Dart engine code. Whether
  `flutter_assets` are stored deflated in the APK is **to be measured** by
  the `--analyze-size` diff.
- **+30 ms cold start**: the dictionary is meant to stay off the startup
  path, so any visible regression means it leaked onto it.
- **50% fewer requests and bytes**: the token-predict request per keystroke
  and the autocomplete POST per debounced keystroke disappear. The remaining
  traffic is printing pages, which the page memo deduplicates.

## 7. Risks and edge cases

- **F1 changes the baseline.** If the old app's search never reaches the API
  on devices, the "old vs new" comparison measures broken against working.
  Q2 has to be settled before M0's numbers are used.
- **Unicode drift.** Node 22 uses ICU 77.1 (Unicode 16.0), `unorm_dart` 0.3.3
  declares Unicode 18.0, and a Rust job would use its own tables. Rows
  shipped as exceptions (611) are immune because their compacts come from
  the generator. Typed queries are covered by `compact.json`, but only for
  the cases in it, so add any new failing input there.
- **Collation drift** for runtime strings (P2): set names, numbers and absorbed
  group names. Watch `paint.json` failures. Extending the fixture with more
  captured hydration rows is cheap.
- **Known engine gaps carried over** (`docs/TYPEAHEAD.md` G1–G7,
  `docs/TYPEAHEAD_AUDIT.md` §U): `Nidoran ♀`/`♂` share the compact `nidoran`;
  numbers/rarity search-page parity is pending; Meili `matchingStrategy`
  behaviour. Parity means reproducing these too, not fixing them in Dart only.
- **Dictionary staleness.** New CardTrader printings add names. Until M7/M8
  exist, the app only knows the names in its bundled asset. Unknown names
  still reach the server through the typed-query lookup in `catalogRecall`
  and the absorbed-names path (`absorbNames`), but without a local prior.
- **Version skew.** An app with an old engine and a new dictionary is the
  normal case after a refresh. `formatVersion` guards the layout only, so
  engine-behaviour changes that need new columns must bump the format and
  keep serving v1 to old apps (Q5).
- **Memory pressure on low-end Android.** The dictionary is small, but the
  printing cache and thumbnails are not. Reuse the web's caps (2,500 names,
  30 min; 128 thumbnails).
- **Isolate start cost.** `Isolate.run` spawns an isolate per call. Its cost
  on the low-end device is **to be measured**. If it exceeds the decode itself,
  decode the disk copy synchronously after the first frame.
- **Satellite games.** The local dictionary is Pokémon-only. Other games keep
  the server path (as the web does, `SearchBox.jsx:322-350`).
- **Web build of the Flutter app.** If `pokemon_card_vault` is still built for
  web, the same code path runs in the browser. There `Isolate.run` is not
  available, so fall back to a synchronous decode, and `Uri.base` is correct.

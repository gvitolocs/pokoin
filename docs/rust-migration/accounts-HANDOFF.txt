1. WHAT THIS IS
---------------
The native Rust replacement for the Node handlers that own accounts, identity,
wallets, the forum, the collection/portfolio BFFs and news comments. Runtime is
axum + reqwest/rustls + Redis, talking to Firebase, Firestore, Supabase
PostgREST and Cloudflare R2 directly over HTTPS.

Hard constraints honoured:
  * no Node process at request time
  * no JavaScript engine
  * no Rust -> Node fallback (a route is either native or not mounted)
  * no placeholder success: an unported route is NOT mounted (404), and a
    missing credential produces a truthful `500 ... is not configured.`
  * nothing in the unported 22 routes is advertised as working


2. ROOT AGENT: HOW TO WIRE IT
-----------------------------
Add ONE line to pokoin-rust/Cargo.toml members (this crate deliberately has no
`[workspace]` table and no `workspace = true` inheritance, so it also builds
standalone):

    "crates/accounts",

Then, in apps/api/src/main.rs:

    let accounts_state = pokoin_accounts::DomainState::from_env();
    let app = pokoin_accounts::router(accounts_state)
        .merge(existing_router);          // order does not matter

Contract you can rely on:

    pub fn router(state: DomainState) -> axum::Router
    pub struct DomainState              // Clone; one Arc inside
    impl DomainState {
        pub fn from_env() -> Self;                                  // production
        pub fn with_transport(AccountsConfig, SharedTransport) -> Self;
        // test/DI builders:
        pub fn with_verifier(Arc<dyn TokenVerifier>) -> Self;
        pub fn with_firestore(Option<Firestore>) -> Self;
        pub fn with_auth(Option<FirebaseAuth>) -> Self;
        pub fn with_supabase(Option<SupabaseClient>) -> Self;
        pub fn with_emails(Arc<dyn EmailSender>) -> Self;
        pub fn with_limiter(Arc<dyn RateLimiter>) -> Self;
        pub fn with_media_store(Option<Arc<dyn MediaStore>>) -> Self;
        pub fn with_clock(Arc<dyn Clock>) -> Self;
        pub fn with_email_config(EmailConfig) -> Self;
    }

The paths inside the router already carry the `/api/...` prefix, so `merge` or
`nest` both work without adding a prefix.

`DomainState::from_env()` NEVER panics. It reads:

    FIREBASE_PROJECT_ID, FIREBASE_CLIENT_EMAIL, FIREBASE_PRIVATE_KEY   (required for anything Firebase)
    POKOIN_REQUIRE_VERIFIED_PASSWORD=1                                 (the password-email gate)
    POKOIN_PENDING_SIGNUP_KEY | PENDING_SIGNUP_KEY                     (falls back to the SA key, exactly like Node)
    PUBLIC_SITE_URL, EMAIL_FROM, NO_REPLY_EMAIL_FROM, ADMIN_SIGNUP_EMAIL, RESEND_API_KEY
    SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY
    VALKEY_URL | REDIS_URL                                             (rate limiting; allow-all when absent)
    R2_FORUM_MEDIA_{ENDPOINT,BUCKET,PUBLIC_URL,ACCESS_KEY_ID,SECRET_ACCESS_KEY}
    POKOIN_FIREBASE_JWKS_URL, POKOIN_OAUTH_TOKEN_URL, POKOIN_IDENTITY_BASE,
    POKOIN_FIRESTORE_BASE, POKOIN_ACCOUNTS_HTTP_TIMEOUT_MS

If the service account is absent, `firestore()` / `auth()` / `supabase()` return
`Err(ApiError)` and only the routes that need them fail — with a truthful 500.


3. REUSABLE INFRASTRUCTURE (commerce worker: read this)
--------------------------------------------------------
Your `crates/commerce/src/auth.rs` implements its own `TokenVerifier` +
`FirebaseVerifier` + `Claims` + `bearer`, and its own `Claim`/`TokenVerifier`
port. This crate now offers the shared version. They are interface-compatible
enough to collapse into one:

    pokoin_accounts::firebase::TokenVerifier
        async fn verify(&self, token: &str) -> Result<Claims, AuthError>;
    pokoin_accounts::firebase::FirebaseVerifier::new(&AccountsConfig, SharedTransport)
    pokoin_accounts::firebase::Claims {
        uid, email, email_verified, pok_email_verified, name, picture, role,
        exp, iat, auth_time, firebase: FirebaseInfo, extra: Map
    }
    pokoin_accounts::firebase::bearer(Option<&str>) -> Result<&str, AuthError>
    pokoin_accounts::firebase::optional_claims(&Arc<dyn TokenVerifier>, Option<&str>)

Differences from your version that you probably want:
  * it rejects a non-RS256 `alg` and a missing `kid` explicitly;
  * it refetches the JWKS once when the `kid` is unknown (Google key rotation);
  * it validates `iat` is not in the future, in addition to `exp`;
  * it exposes the Node password gate as
    `Claims::password_account_requires_verification()` and
    `Claims::assert_active_password_account(require_verified)`, which returns
    the Node 403 + `auth/pokoin-email-not-verified` code;
  * `ServiceAccount` gives you a cached OAuth 2.0 access token and
    `create_custom_token(uid, claims)`.

Firestore (this is what you asked for):

    pokoin_accounts::firestore::Firestore::new(&AccountsConfig, SharedTransport,
                                               Arc<ServiceAccount>, RetryPolicy)
    firestore.doc("users/u1").get() / .set(DocData, merge) / .create(..) / .update(..) / .delete()
    firestore.run_query(&Query::collection("x").where_eq("uid", uid).limit(2)).await?
    firestore.run_transaction(|tx| Box::pin(async move { ... })).await?
        // tx.get_doc(&ref) / tx.get_query(&q) / tx.set / tx.update / tx.create / tx.delete
    DocData::new().string(..).int(..).bool(..).server_timestamp(..).increment(..).array(..)
    Value::{Null,Boolean,Integer,Double,Timestamp,String,Bytes,Reference,GeoPoint,Array,Map}

Semantics that were preserved on purpose: int64 travels as a string; `set(merge)`
sends an `updateMask`; `serverTimestamp`/`increment`/array union-remove become a
second `transform` write in the same commit; `create` uses
`currentDocument.exists=false`; a transaction with no writes is rolled back
(releasing read locks); `ABORTED` at either the body or the **commit** retries
the whole body up to 4 times with backoff, then surfaces the same 500 Node did.

MONEY (round 2): the referral rewards, the chat payments and the wallet merges
all write `balances/{uid}` + `ledger_entries` inside ONE Firestore transaction
with an idempotency gate (`referrals/{uid}.status`, or
`payment_operations/{sha256(uid\0clientToken)}`) — the same contract
`store::apply` implements. There is a `LedgerSink`-shaped seam at each call site
(handlers/referral.rs `settle_referral`, handlers/chat.rs the `action=pay`
transaction) if you would rather route them through the commerce worker's
`store::apply`; the two call sites are small and already inside a transaction.

MONEY: I did NOT create any SQL ledger table and did NOT fork money persistence.
Wallet sign-in/link still seed and merge the Firestore `balances` document
exactly as Node did (`increment(0)` seed on first sign-in, integer merge for a
claimed `wallet:0x...` account). Your `store.rs` (`LedgerOp` + `apply` over
`pokoin_account_balances` / `pokoin_ledger_entries`) stays the single money
writer. If you want those two Firestore writes to go through your ledger
instead, the call sites are `handlers/wallet.rs` inside the two transactions —
they are small and isolated.

Also public and reusable without pulling in the router:
  * `pokoin_accounts::domain::collection` — the single source of truth for
    `user_card_collections`: `list_owned_collection`, `summarize_owned_collection`,
    `remove_owned_collection_item`, `set_owned_collection_trade`,
    `scan_ownership_doc_id`, `physical_payload_from_scan_row`,
    `is_nft_document`, `iso_timestamp`. The scan/listing workers should use this
    instead of writing their own ownership doc math (it keeps the "absolute

    invariants from D000069/D00006A).
  * `pokoin_accounts::identity::FirebaseAuth` — Identity Toolkit admin
    (`get_user`, `get_user_by_email`, `create_user`, `update_user`,
    `delete_user`, `set_custom_user_claims`) with Admin-SDK-shaped error codes
    (`auth/user-not-found`, `auth/email-already-exists`).
  * `pokoin_accounts::domain::crypto` — native EIP-191 `personal_sign`
    recovery (replaces `ethers.verifyMessage`), address/nonce/session rules.
  * `pokoin_accounts::supabase::SupabaseClient` — PostgREST with the Node
    `encodeFilterValue` escaping and status mapping.
  * `pokoin_accounts::r2::{R2MediaStore, MediaStore}` — SigV4 `PUT`.
  * `pokoin_accounts::rate_limit::{RateLimiter, RedisRateLimiter, AllowAllRateLimiter}`
    — `limitBestEffort` semantics (allow on store failure).

7. FIDELITY NOTES (differences you should know about)
-----------------------------------------------------
* Forum media: `image` 0.25 writes lossless WebP; Node used
  `sharp(...).webp({quality: 86})` (lossy). Pixels, `mime_type`, `width` and
  `height` match; byte size is larger. Switch to a lossy encoder if that matters.
* `ensure-username`: the deployed Node module imported `usernameForRequest` from
  `_username.js`, where it does not exist — it would have thrown a TypeError. The
  port implements the documented contract (claim an explicit handle, else repair
  or assign one). Flagging it because it is a live bug, not a porting choice.
* A Firestore `ABORTED` is retried up to 4 times (including at commit time); an
  exhausted conflict still surfaces as the 500 the Node runtime produced.
* `verify-email-signup` keeps Node's redirect rule (`startsWith('/')` only), which
  does let `//host` through — preserved as-is rather than silently tightened.

10. ADDENDUM — COMMERCE RECONCILIATION (written after reading the commerce
    worker's Honcho revisions rev2/rev4/rev5 on 2026-10-08)
--------------------------------------------------------------------------
The coordinator corrected the commerce worker to keep every Node-era contract in
Firestore and to stop migrating money to new SQL tables. That matches this crate:
no SQL ledger was created here, and wallet sign-in/link still seed and merge
`balances/{uid}` exactly as Node did. The two crates therefore agree on the money
contract. Three concrete integration points remain:

(a) DUPLICATE FIRESTORE CLIENT. `crates/commerce/src/firestore.rs` now exposes
    `FirestoreClient`, `encode_value`/`decode_value`, `FirestoreWrite`,
    `FieldTransform`, `commit_body` and `MAX_WRITES_PER_COMMIT = 500`, while this
    crate exposes `Firestore`, `Value`, `DocData`, `FieldValue` and
    `Transaction`. Two clients over the same REST API is the main duplication to
    remove. Recommended: keep `pokoin_accounts::firestore` (it has transactional
    reads via `batchGet`/`runQuery` sharing one transaction id, `ABORTED` retry
    at commit time, per-request retry policy, cached OAuth with 401
    invalidation) and delete commerce's, or vice versa — but do it in one pass,
    not route by route, so the two do not drift. Adding `MAX_WRITES_PER_COMMIT`
    style batching to the accounts client is a small follow-up if commerce needs
    it (this crate currently issues one write pair per document).

(b) SAME BALANCE DOCUMENTS, DIFFERENT DISCIPLINE. `commerce/src/store.rs`
    `LedgerOp` + `apply` moves PKN through `balances/{uid}` +
    `ledger_entries/{id}` + `commerce_idempotency/{sha256(key)}` inside one
    Firestore transaction, which Firestore serialises against any concurrent
    transaction touching those documents. The accounts wallet flows
    (`handlers/wallet.rs`, `wallet-auth/verify` and `wallet-link/complete`) also
    read and write `balances/{uid}` inside `run_transaction`, and — exactly like
    Node — they are NOT idempotency-keyed: they compute a source amount and then
    `increment` it onto the target. Two concurrent claims of the same wallet-only
    account are still safe (the registry precondition plus Firestore transaction
    retry), but a *simultaneous* transfer out of the source wallet-only account
    could interleave with the merge. Node had the same window. If you want it
    closed, move the merge in `wallet-link`/`wallet-link/complete` behind
    `commerce::store::apply` (a Transfer from `wallet:0x...` to the account uid
    with an idempotency key like `wallet_merge:{address}:{uid}`) once the two
    Firestore clients are unified. The call sites are two small blocks, both
    already inside a transaction, so the change is contained.

(c) THE `bank` / IDEMPOTENCY COLLECTIONS THIS CRATE WRITES are only
    `pending_email_signups`, `pending_email_signups_by_email`,
    `wallet_auth_nonces`, `wallet_addresses`, `wallet_link_sessions`, `users`,
    `usernames`, `balances`, `user_card_collections`, `news_comments` — the same
    names Node used, and the same names commerce now uses for `users`,
    `usernames`, `wallet_addresses` and `balances`. No new collection name was
    invented by this crate. If you unify on one Firestore client, assert these
    document shapes in a shared test so a change in either crate cannot silently
    break the other.
